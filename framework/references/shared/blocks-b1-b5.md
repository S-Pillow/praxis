## **Block B1 - Evidence Attribution Labels**

Every material evidence item or observation carries one attribution label: agent-observed, tool-observed, operator-observed, operator-attested, inferred, or not observed. In these labels, operator-observed and operator-attested mean observation or attestation by a named authorized human observer, including a decision owner or Human Reviewer; they do not assign the formal Operator / Admin / Maintainer role or grant action/decision authority. Retain the observer's actual identity and role. A claim/result may cite multiple evidence items with different attributions; do not collapse them into one invented source. Attribution identifies who or what observed an evidence item; it does not by itself prove the claim. Also classify material evidence purpose under Section 7 Evidence purpose and sufficiency when it affects routing. Preserve the verification chain only to the strength required by that purpose: claim -\> source/provenance -\> verification method -\> verification result -\> acceptance interpretation. A verified result means only that the stated method produced the stated result; do not silently broaden it. Attested evidence stays attested; authoritative upstream evidence stays upstream evidence unless locally observed. Material handoff/control-state assertions that can affect routing, acceptance, reconciliation, or the next action also state an assertion basis when ambiguity exists: current-observation, current-source-derived, governing-artifact-derived, historical-evidence, or inferred. This basis is separate from B1 observer attribution. A requirement stated in a specification, for example, MUST NOT be presented as current or historical implementation evidence unless that implementation is independently supported.

## **Block B2 - Status Vocabulary**

Status has four dimensions; a value or field from one must not substitute for another. 1) Execution outcome (scalar): PASS / PASS WITH NOTES / PARTIAL / FAIL / BLOCKED. 2) Durability/closure state (independent fields, not one enum): source = not-established / working-state / source-durable / n-a; shared = not-established / shared-durable / n-a; artifact = not-established / artifact-built / n-a; release = not-established / deployed / n-a; finalization = complete / pending / n-a. Record every applicable field; deployment does not imply source durability, and artifact existence does not imply shared/synchronized state. 3) Evidence state: achieved = not-established OR any supported set drawn from implemented / tested / source-verified / artifact-verified / production-verified / operator-validated; pending_required_observation = none / named-observer-pending. Achieved evidence is cumulative only to the extent actually supported; a pending observer must not erase source/artifact/production evidence already achieved. 4) Control disposition (scalar): accept / correction / reconciliation / observer check / decision request / stop. Complete and done are prohibited collapsed states. Accepted limitations are owner/risk/acceptance decisions alongside B2, not evidence values. The confirmed project-state controls define the mechanism and closure signal behind each durability/closure field; use the capability profile when Platform Capability controls are active.

### Deterministic outcome assessment

Assessment rule. Retain the executor-reported outcome and original handoff/direct execution report unchanged as evidence; if no report exists, record that absence without inventing an outcome. Under orchestration, the Prompt Agent applies the first matching row below; in direct execution, the executing agent performs the same reconciliation without inventing a second role. Record the assessed Execution outcome and Control disposition using Block B2, the applicable row, evidence, and reason for any difference from the executor report in the existing Project Control Record/evidence surface. Neither a reported PASS nor completed useful work overrides a higher-precedence violation. Scope all stops under Section 5.

Outcome storage. When a distinct Builder exists, Builder Handoff outcome fields retain the executor report; in direct execution, retain the executor report/result separately in the existing evidence surface. The Project Control Record stores the assessed Block B2 outcome/disposition plus all applicable durability/closure fields, achieved evidence, pending_required_observation, the report reference, and discrepancy reason when different. A confirmed violation remains FAIL for that unit after reconciliation; corrective work has its own result. For stale state, apply Section 5.4 read/guard/reconciliation before dependent work. For observer check, preserve achieved evidence and set pending_required_observation = named-observer-pending until the assigned evidence arrives. A correction disposition identifies needed work and does not grant new authority.

## Block B3 - Source / Artifact / Deployment Identity

Where identity matters, record the applicable source revision/state marker (commit/tag/platform version/fingerprint or equivalent), branch/synchronization state when applicable, build/run/review request ID, artifact path/name, artifact version, SHA-256 checksum when practical, provenance-stamp source, and deployment/release ID. State-bound evidence: an external review, scan, test, or evaluation is evidence for the exact source/version/state and material configuration it examined; any change capable of affecting its claim invalidates that evidence for the new state unless dependency analysis proves the evidence transferable. Derived evidence copies: when an authoritative artifact must be intentionally transformed for inspection or transport (for example decryption, Save As, decompression, redaction, format conversion, or signature removal), retain the original identity separately, record the transformation and derived-copy identity, and state which claims the transformation preserves. The derived copy may support preserved content/visual claims but MUST NOT prove original byte identity, signature, encryption, packaging, or provenance properties that the transformation changed.

## **Block B4 - Rollback Readiness Levels**

Identified: known prior state. Selectable: visible and selectable. Actionable: an authorized restore/redeploy/reinstall/recovery action is documented well enough to execute. Proven: recovery succeeded, was rehearsed, or independently verified in an equivalent environment. Required level is risk/consequence-based. Use the least-complex mechanism that meets the required level; do not invent selective per-file restore, extra backups, repositories, or stronger recovery solely for AIPF completeness. Falling below the required level blocks only the release/change that depends on that recovery unless explicitly accepted.

## **Block B5 - Semantic Gate and Non-Execution Evidence**

Gate/condition - ; allowed-path assertion - ; forbidden action - ; direct non-execution evidence method - ; owner and evidence attribution (Block B1) - ; result pass / fail / partial / deferred. Absence of visible output alone is not evidence.
