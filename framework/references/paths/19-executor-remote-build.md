# **Chapter 19 - Executor and Remote Build Integrity Path**

When to use: an AI executor moves large files in chunks, watches a remote CI/build/test/package/deployment job, waits for asynchronous work, or downloads artifacts. These rules apply to any stack: web bundles, desktop executables, mobile builds, server packages, generated reports, migration bundles, installers, model artifacts, and documentation builds.

Companion chapters when applicable: Ch. 16 for release retry/tag provenance; Ch. 20 at release.

## **19.1 Rules**

Chunked transfer integrity. When an executor moves, rewrites, or reconstructs a large file through limited-size chunks or repeated tool calls, define the expected target and verify final integrity before claiming completion -SHA-256 or equivalent checksum when practical, recording source path, destination path, transfer method, byte/line expectations, and checksum result.

Remote job/evaluation monitoring. Apply Section 7 Condition-based synchronization. Prefer provider-native completion/event/wait mechanisms when available. Otherwise use bounded observation with an explicit maximum duration and, when polling is necessary, adaptive intervals: do not poll faster while state is unchanged; lengthen the interval within the authorized window and reset/shorten it after a meaningful transition. Record method, run/review identifier or URL, exact source/version/state evaluated, trigger, terminal state, duration, and produced artifact/finding location when applicable. Terminal states include success, failure, cancelled, timed out, skipped, blocked, unavailable, and stalled when the provider can distinguish them. Never poll merely to demonstrate attentiveness.

Remote failure/retry discipline. Before rerunning a failed build/test/package/review/evaluation, classify the failure as source regression, stale expectation, fixture/test/review-definition defect, environment/dependency failure, infrastructure/transient failure, or unresolved. An unchanged retry is appropriate only when evidence supports an operational/transient cause or intentionally probabilistic behavior. Source/test/review-definition defects require a corrective delta or refreshed controlling state before rerun. A controlled retry on the same exact immutable state may recover an operational evidence mechanism; repeated operational failure does not authorize indefinite retries - use an authorized capable fallback or apply the governing missing-evidence disposition.

Exit-code authority and raw status. Section 7 (Raw command status) governs: exit codes, failed assertions, and CI terminal states are authoritative; stderr and progress output are diagnostic - some tools write normal progress to stderr.

Constrained-agent monitoring. If the agent cannot observe a remote job to terminal state (network, API, authorization, cache, UI, or tool limits), do not claim direct terminal verification. Name an authorized capable evidence actor, tool, or trusted channel, define the exact evidence required, and attribute the result under Block B1: operator-attested for a human attestation, operator-observed for retained human observation, or the applicable tool/source attribution. Unavailable evidence remains not observed; never convert attestation into direct agent observation.

External evaluation freshness. Automated or external review/evaluation evidence is valid only for the exact immutable source/version/state and material configuration it examined. Amend, rebase, force-push, replacement, configuration change, or any state change capable of affecting the evaluated claim invalidates that evidence for the new state. A clean review of a superseded state cannot close the current gate; re-evaluate only the affected evidence when dependency analysis proves the remainder transferable.

Release retry provenance. If a failed remote build requires moving or recreating a tag, release, or artifact pointer, rerun provenance checks after the retry per Chapter 16.2 - the published release claim reconciles against the built artifact, not only the source/version/state record.

Playbook. 1. Classify the executor work: chunked transfer, remote CI/test/build/package/deployment, automated/external review or scan, artifact download, or async verification. 2. For transfers: define source, destination, expected size/lines, and checksum before claiming intact. 3. For remote jobs/evaluations: start from a known source revision/version/state; record provider, job/review, run/request ID or URL, trigger, and exact evaluated identity. 4. Apply Remote job/evaluation monitoring to observe terminal state and Remote failure/retry discipline before rerun; treat raw terminal status as authoritative per Section 7. 5. If unobservable, apply Constrained-agent monitoring and Block B1 attribution. 6. Bind external evaluation freshness to the exact state reviewed. 7. Verify any produced artifact in its target use mode; report source verification, artifact verification, and operator validation separately (Block B2).
