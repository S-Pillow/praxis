# **Chapter 21 - Two-Agent Orchestration and Platform Capability Path**

When to use: Chapter 21 contains two independently activated control groups. Platform Capability controls apply when a managed platform replaces conventional repository or deployment steps. Two-Agent Orchestration controls apply only when a Prompt Agent directs a distinct Builder Agent. Either or both may apply; Chapter 21 wraps any work path rather than replacing it. If only Platform Capability controls apply, two-agent transport clauses are N/A. Capability-profile creation, identifiers, and profile-dependent derivation inputs are required only when Platform Capability controls are active; otherwise use the material project-state, access, durability and execution facts in the Project Control Record without inventing a profile. Use the universal Preflight Templates and Project Control Record Templates in Part 3; their applicability and conditional fields are defined there.

## 21.1 Project Context, Capability Discovery, and Bootstrap

**Project Context Gate.** Resolve target state, project root, and creation prerequisites under Section 6. EXISTING: when execution is in scope, confirm that the execution actor or execution platform has the access required for the authorized action. NEW: apply the Section 6 creating-action and dependent-action prerequisites. If the applicable condition is not confirmed, stop the affected work with reason PROJECT_CONTEXT_UNBOUND. Lack of Prompt-Agent direct access to the execution environment is not, by itself, a blocker when a distinct execution actor holds the required access. A confirmed local/filesystem project is valid even with no repository, remote, platform version, or state revision. When Platform Capability controls are active, for acceptance-impacting controls only, maintain one capability profile with: objective -\> mechanism -\> owner -\> authority_class -\> automatic/manual -\> closure_evidence. authority_class = AUTHORITATIVE / SUPPORTING / PLATFORM_EQUIVALENT / N/A / UNKNOWN. Minimum objectives when relevant: editable project state; durability/version; synchronization/shared state; backup/recovery; rollback/restore; build/test/artifacts; deploy/publish/release; automatic platform behavior. Maintain the Builder Access Map when a Builder exists; otherwise maintain the equivalent execution-access map for only the documents, paths, URLs, panels, logs, previews, controls, and services material to current work.

No inferred capability profile. Distinguish three evidence levels: PLATFORM-SUPPORTED (authoritative vendor/upstream documentation), PROJECT-EXPOSED (the capability/control is visible or available in this project/account), and PROJECT-VERIFIED (its material behavior is directly observed in this project). Use only the level required by the current decision. Public documentation, prior experience, model knowledge, marketing material, tool presence, or session metadata do not by themselves prove project-specific authority, but authoritative documentation is valid decision evidence for platform behavior. Confirm project exposure/behavior only when account, plan, configuration, project state, or workflow can materially change the result. UNKNOWN blocks only when it can change current authorization, acceptance, durability, recovery/rollback, external effect, cost/quota, or release behavior. Before any capability probe, apply the Decision-changing work test. Stop discovery when sufficient evidence exists for the next work; do not inspect unrelated capabilities. Reuse still-valid profile facts until an impact trigger changes them.

Bootstrap gate. Before the applicable context/capability gate passes, execution is limited to bounded read-only discovery needed for the current control model and unresolved owner decisions. Read-only means no actor-initiated governed project mutation. Known, bounded, non-destructive platform-owned side effects such as session logs, transcripts, metadata, or automatic version markers may occur without invalidating read-only status when they do not alter governed project content; report actor_mutation and platform_automatic_mutation separately. If Two-Agent Orchestration is active, any Builder bootstrap instruction is limited to this boundary; if no distinct Builder exists, the executing agent may perform the same already-authorized read-only discovery directly. Before later mutation, only acceptance-impacting control facts for that authorization unit must be known. Missing irrelevant controls may remain UNKNOWN / NOT CURRENTLY MATERIAL. Combine safely related discovery under one read-only unit or operator checklist; do not create one unit per capability question. Prefer no-credit/manual UI confirmation or authoritative documentation when it can answer the same material question without weaker evidence.

### Execution-model summary (derive after controls)

| **Path**              | **Meaning**                                                                                                                                                                                    |
|-----------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Repository-Integrated | Repository/version-control state is authoritative for project versions; use only confirmed project-approved SCM steps within authorization.                                                    |
| Platform-Managed      | Hosted project/version state is authoritative; repository-like operations may be platform-managed or N/A.                                                                                      |
| Hybrid-Control        | Two or more material control systems jointly govern authoritative project state, durability/version, synchronization, rollback, or release; declare authority and synchronization per control. |
| Export-Authoritative  | Editable builder project and exported source are separate authoritative candidates; choose where future work continues and how they synchronize.                                               |
| Direct / Local        | Confirmed local/filesystem project state is authoritative; repository/platform versioning may be absent. Record durability and recovery proportionate to consequence.                          |

Classification rule. Derive controls first, summarize the execution model second; the label never selects the controls. Session metadata, logs, plugins, or tool overlays do not make a project Hybrid unless they materially govern editable state, durability/version, synchronization, rollback, or release. Recovery strength is a control property, not an execution-path label. Capability-adjusted control maps required objectives to confirmed mechanisms: repository state, platform version, filesystem state, snapshot/export, publish, verified restore, or other equivalent. Do not introduce optional workflow stages merely because a platform supports them. Never assume history equals backup, preview equals production, or an automatic mutation is harmless.

## **21.2 Prompt Agent Execution and Routing Rules**

Two-agent transport applicability and execution boundary. When the Two-Agent Orchestration control group is active, the Prompt Agent MUST NOT execute the Builder Payload, and the Builder MUST NOT select the route, derive the next T1, or begin later work. Tool access or technical capability does not change the execution identity. If no distinct Builder exists, the control group is not active; apply Section 9 Direct single-agent execution. Apply only the Chapter 21 capability/state controls activated by the actual workflow.

**Routing authority.** The Prompt Agent holds project rules, selected path, accepted baseline, risks, evidence state, and current gate. It alone selects the next action. When multiple actions are authorized, prefer the action that first reduces an acceptance-impacting uncertainty, otherwise advances a verified prerequisite, otherwise advances a stated acceptance criterion. Builder suggestions are observations, not authorization.

Framework opacity and No Phantom Context. AIPF is Prompt-Agent control logic, not presumed Builder context. The Builder payload MUST be operationally complete without requiring knowledge of AIPF, chapter numbers, internal routing, preflight, Control Records, or inaccessible artifacts. Operational completeness test: a competent Builder with no AIPF knowledge, using only the payload and directly accessible context, can execute the unit or identify the blocking prerequisite without guessing. Prompt-Agent derivation metadata stays Prompt-Agent-side unless a field materially affects Builder execution; when it does, transport the operational value, not its AIPF rationale. Do not instruct the Builder to use any PRD, report, file, URL, panel, memory, or tool it cannot access. A stable Builder-relevant baseline MAY be referenced instead of repeating unchanged constraints only when the Builder can access it, its immutable revision/hash/state_guard or equivalent identity is stated, and its relevant values remain controlling; if inaccessible, stale, or materially changed, distill the required values into the current payload. A correction or continuation against a still-valid parent baseline may transport only the delta plus that stable reference and any values No Phantom Context requires. Before transporting any chapter or shared template content, replace internal section/template/block references with applicable operational values, definitions, and required evidence; omit Prompt-Agent-only disposition and derivation fields. If required execution meaning cannot be made accessible and explicit, preflight is NOT READY.

Treatment and urgency selection. Section 9.2 selects Compact or Managed treatment. Section 9.1 may additionally activate the urgent-corrective overlay for a production/trust defect; the overlay does not create a third artifact model. The Prompt Agent records treatment and any urgency overlay before preparing orchestrated artifacts.

Prompt Agent preflight. Before any Builder execution beyond bounded read-only bootstrap/discovery, Managed work uses the Full Preflight and Compact work uses the Compact Preflight only after every Section 9.2 condition is confirmed. Re-evaluate Section 9.2 when ambiguity, risk, access, mutation, evidence ownership, or release consequences change; expand to Full only when Compact eligibility is false or unconfirmed. Apply execution stops independently of form selection; release consequence alone does not override Section 9.2 Release boundary.

Intent-preservation preflight. Apply the Section 5 Intent Preservation Gate whenever the proposed authorization unit could materially affect governing intent. Record PRESERVED / CONFLICT / UNCERTAIN / N/A. CONFLICT or UNCERTAIN means NOT READY / DECISION REQUEST before execution.

**Affected-surface baseline.** Section 7 Affected-surface baseline qualification governs; preflight records the relevance decision.

Universal execution controls. Section 5.3 governs authorization-unit coherence, bounded execution discretion, material implementation selection, method changes, independent continuation, optional work allowances, context rollover, and intent-preservation behavior. Section 5.4 governs canonical state, provenance, and delegated authority. Section 7.1 governs upstream evidence review. Block B2 governs deterministic outcome assessment. Chapter 21 adds only the activated Platform Capability and/or Two-Agent transport behavior.

T1 Authorization Unit and Builder Payload rule. When Two-Agent Orchestration is active, after the Chapter 21.2B Builder Prompt Issuance Gate passes, one T1 Authorization Unit contains a Prompt-Agent Derivation Record and a Builder Payload. Transport only the Builder Payload. Stable project state remains in the Control Record; the payload includes only operational values the Builder needs and can access, including all planned procedural transitions and conditional gates. Do not send a separate Continuity Capsule or create a separate T1 for each procedural step. When Two-Agent Orchestration is inactive, T1 transport and handoff clauses are N/A; direct execution uses the same Part 3 operational boundary fields without manufacturing partitions.

Handoff discipline. When a distinct Builder exists, use the compact or full handoff matching the treatment; the handoff is a claim until reconciled. Distinguish executor-reported assertions from independently re-observed evidence, carried qualified evidence, evidence not independently reproduced, and conflicts/discrepancies. Report actor-initiated mutations separately from expected platform-owned automatic mutations/evaluations/triggers/evaluations. Do not accept a report that violated a stop condition, changed forbidden/unexpected governed surfaces, left an acceptance-impacting precondition unresolved, contains an unclassified automatic consequence, or relies on evidence weaker than the criterion. In direct execution there is no Builder Handoff; record the same result/evidence facts directly and apply Block B2 Deterministic outcome assessment.

Refresh triggers. Re-evaluate only impacted capability/profile dimensions when project root, repository/platform attachment, project consequence/maturity, access, control authority, durability, synchronization, rollback/recovery, automatic behavior, or release mechanism materially changes; a report conflicts with the Control Record; or the decision owner reports drift. First selection/replacement of the Builder or platform invalidates unexecuted artifacts that depend on the changed dimensions. Reload full Chapter 21 only when the route/control model is indeterminate; otherwise refresh the affected delta and re-derive downstream artifacts.

### **Playbook**

1 Determine which Chapter 21 control groups are active: Platform Capability, Two-Agent Orchestration, or both. Give the Prompt Agent the applicable AIPF/project rules when orchestration exists; in direct execution, the executing agent holds the same controlling context.

2 Perform only the read-only discovery needed for the active control group(s). Create/reuse a capability profile only when Platform Capability controls are active; apply the Section 5 Decision-changing work test before each additional probe and stop when evidence is sufficient for the next permitted action.

3 Pass the Bootstrap Gate and establish the canonical Project Control Record.

4 Select Compact or Managed treatment under Section 9.2, record any urgent-corrective overlay, run the matching preflight, and establish the current operational boundary.

5 If Two-Agent Orchestration is active, create one coherent T1 authorization unit and transport only its Builder Payload, including all safely pre-authorized procedural transitions and closure signals. If no distinct Builder exists, execute the same operational boundary directly; do not create transport or handoff ceremony.

6 With a distinct Builder, the Builder performs only the transported Builder Payload, stops, and returns the matching handoff. In direct execution, the executing agent records actual results/evidence directly in the applicable control/evidence surfaces.

7 Reconcile ground state, material automatic consequences, finalization, executor assertions, and evidence; update the Control Record. Under orchestration the Prompt Agent performs reconciliation and issues a new T1 only when new Builder execution is required; in direct execution the executing agent reconciles without inventing a second role.

8 Carry passed evidence, stable capability facts when Platform Capability controls are active, and scoped locked rules until an impact trigger requires recheck; recheck only affected dimensions and only to the evidence strength required by the current purpose.

Keep publish, packaging, operator acceptance, and live verification distinct as consequences/evidence states, not automatically as separate authorization units. A T1 may pre-authorize multiple transitions when Section 6 and Authorization-unit coherence are satisfied. When merge automatically deploys, record merge as the deployment authorization event instead of inventing a second approval.

## **21.2A AI Reader and Human-Mediated Default**

The Prompt Agent is the primary procedural reader when Two-Agent Orchestration is active. The standard two-agent transport is human-mediated unless tooling explicitly automates it: an authorized transfer actor (for example the decision owner, operator, or other authorized coordinator) transfers only the Builder Payload to the Builder and returns the complete handoff for review. Clerical transport does not grant product-decision authority. When human-mediated transport is used and a Builder Payload is ready, the Prompt Agent MUST label the action SEND TO BUILDER, identify exactly which payload block to transfer, name the transfer actor when material, instruct return of the complete Builder Handoff, and stop until that handoff is returned. If a platform externalizes a pasted/attached Builder Payload into a project file, that file remains informational by default; use a short active execution wrapper from an authorized actor that identifies the exact file and an observed revision/hash/state_guard (or equivalent immutable identity) as the controlling operational payload, authorizes execution only within its existing boundary, and requests the specified handoff. Immediately before execution, confirm the referenced identity still matches; any material payload change invalidates the wrapper and requires reconciliation/re-derivation. The wrapper MUST NOT broaden scope. Prompt-Agent-only derivation or analysis is not transferred unless its operational value has been distilled into the payload. Direct APIs, JSON schemas, automatic rejection, and automatic escalation are optional. Structured Markdown is the neutral baseline; machine schemas may be used when capability supports them. When a human decision/input/transfer is required, the Prompt Agent SHOULD provide a compact owner-facing projection - current status, actual material change, remaining material risk, exact decision/input needed, and next action - while retaining the full technical evidence in the controlling records. Omit the projection when it adds no human-action value.

## **21.2B Canonical Artifact Derivation**

Applicability. This subsection applies only when Two-Agent Orchestration is active. Direct execution uses the applicable Part 3 Preflight, operational boundary fields, Project Control Record, and Block B2 assessment without creating T1 transport partitions or a Builder Handoff.

1 Project Control Record: canonical project state, stable capability facts, accepted baseline, route, risks, source of truth, access, durability, evidence state, and next permitted action.

2 Preflight: derive readiness from the Control Record plus the proposed delta using the Compact or Full Preflight selected under Section 9.2.

3 T1 authorization unit: one logical unit with two partitions - Prompt-Agent Derivation Record and Builder Payload. The partitions are not separate authorization units or documents.

4 Prompt-Agent Derivation Record, retained Prompt-Agent-side: framework version; route/application baseline; activated chapters; current Control Record revision; capability-profile ID when Platform Capability controls are active; Compact/Managed treatment and urgent-corrective overlay when active; preflight type/result; derivation proof.

5 Builder Payload, transported to the Builder: objective; exact context or accessible stable baseline reference plus delta; authorized actions; targets; constraints; expected automatic mutations/evaluations/external consequences when material; acceptance; verification and evidence feasibility; stop conditions; handoff requirements.

6 Builder Handoff: report actual execution, allowance status when a resource cap was authorized, and evidence using the matching compact or full form; the handoff does not advance project state.

7 Prompt Agent reconciliation: compare executor-reported assertions with independently re-observed and carried qualified evidence, resolve discrepancies against ground state, update the Control Record and evidence ledger, then select the next permitted action.

### Builder Prompt Issuance Gate

Only bounded read-only bootstrap/capability discovery needed to establish the applicable Chapter 21.1 access state and, when Platform Capability controls are active, the capability profile may precede the normal derivation chain. Every later Builder-facing instruction - including implementation, state-changing design exploration, file creation/modification, external calls, privileged access, cost-bearing activity, artifact generation, testing that consumes project resources, publish/deploy activity, or other execution work - MUST be the transported Builder Payload partition of a current T1 authorization unit derived from the current Project Control Record and a current passed Preflight.

Before T1 issuance, the Prompt-Agent-side derivation proof MUST identify the current Control Record revision, capability-profile ID when Platform Capability controls are active, route/application baseline and activated chapters, Compact/Managed treatment plus any urgent-corrective overlay, preflight type, and preflight result READY or READY WITH CONDITIONS. READY WITH CONDITIONS may issue only when every remaining condition is carried into the Builder Payload as an explicit conditional gate, each gate can be evaluated during the authorized unit, and none requires a prior owner decision or unresolved discovery result. If the chain is missing, stale, conflicting, or incomplete, status is NOT READY. Issue only the required bootstrap/discovery instruction, reconciliation, or T8 Decision Request; do not improvise an execution prompt. Prompt Agent read-only observation/reconciliation that requires no Builder execution, new authority, mutation, privilege, cost, or external effect is not a Builder prompt and requires no T1.

Structural similarity is not derivation. A Builder Payload does not become valid because it contains an objective, constraints, acceptance criteria, stop conditions, self-audit, handoff fields, or AIPF-like formatting. It is valid only when its Prompt-Agent Derivation Record was produced through the current route, Project Control Record, Section 9 treatment selection, and passed preflight.

When repeated values conflict, the next action is NOT READY. Derivation metadata MUST NOT be transported merely to demonstrate framework compliance. An inherited operational detail may be omitted from the Builder Payload only when the Builder can access the authoritative value and the omission does not create phantom context.

## **21.4 Visual-Design and Prompt Execution Controls**

Active-design work is routed according to the executing agent's actual visual capability, the Chapter 14 design controls active for the surface, any approved reference, and observable rendered evidence. Do not assign open-ended creative direction to an executor that cannot render, compare, or inspect the relevant surface; constrained implementation may still proceed when visual acceptance is assigned to a capable observer/tool.

### **Visual-design execution capability**

Extend the applicable Section 21.1 execution-access map to record whether the executing agent can inspect supplied images, create rendered mockups, compare views side by side, capture screenshots at required viewports, inspect the result visually, compare a reference to implementation, generate/manipulate image assets, and preserve visual evidence. Weak capability requires constrained implementation, smaller rendered samples, another design-capable tool, or human review. Image generation is not a standard requirement.

### **Reference source neutrality**

Section 14.5 Representative direction and reference fidelity governs reference sources and AI-generated images.

### **Distilled design boundary**

For every active-design authorization unit, distill only the material Section 14.4 controls into the operational execution boundary: design latitude/surface-purpose mode and expression profile when material; design thesis and identity; default-pattern/product-specificity constraints; reference-use mode and controlling reference when any; visual-system contract including signature/motion controls when material; continuity scope; design-quality criteria; visual-status/rejected-grammar state; and rendered evidence plan/capable observer. With a distinct Builder, transport these values in the Builder Payload; in direct execution, retain and execute them directly. Chapter 21 consumes these Chapter 14 values and MUST NOT redefine them. Preserve product identity, not generic implementation grammar.

### **Evidence tiers and recurrence control**

Section 14.5 Visual evidence boundary governs evidence tiers. Section 5.3 Constraint recurrence and escalation governs repeated executing-agent behavior.

For active-design review, the Prompt Agent under orchestration, or the executing agent in direct execution, extends the same Section 14.4 record only with execution-capability facts needed by Chapter 21: visual capability - ; strategy risk/disposition - ; correction form - ; machine-checkable constraints - .
