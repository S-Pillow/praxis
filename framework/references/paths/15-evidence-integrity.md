# **Chapter 15 - Evidence, Data, and Finding Integrity Path**

When to use: any feature that produces findings, classifications, alerts, risk scores, extracted entities, recommendations, scanner results, or business evidence; and any data, record, upload, import, export, or report whose payload contains a derived, classified, inferred, ranked, scored, summarized, promoted, or suppressed value that could reasonably be relied upon as evidence, judgment, recommendation, or authoritative result. Ordinary file exchange and purely mechanical formatting or totals with no such reliance-sensitive payload use Template T7 with the applicable application path. Any output that could be mistaken for a real prediction, recommendation, diagnosis, or authoritative answer also activates this chapter.

Companion chapters when applicable: Ch. 20 at release; template T7 for any import/export feature. The goal is not to make every product forensic - it is to prevent unconfirmed candidates, malformed responses, skipped work, or implementation claims from becoming trusted results.

## **15.1 Data, Record, Upload, and Report Rules**

Collected field resolution. When a collected field appears unused, do not default to removal. Classify the intended resolution: display, workflow logic, search/filter, reporting/export, reference/history, compliance, future/deferred, or remove. Removal requires explicit approval, confirmed redundancy, confirmed lack of business purpose, or rejected/out-of-scope classification.

**Record lifecycle.** Governed by Section 2 (Created records need an explicit lifecycle policy) and Template T4. Evidence-specific addition: do not infer that audit or evidence controls require permanent business records.

File and data exchange. Apply the Section 2 file/data-exchange requirement and Template T7. Evidence-specific additions for this chapter: imported or extracted records enter the candidate lifecycle (15.2) rather than arriving as confirmed findings; exported findings carry their provenance fields and truth classification; report tests verify the exact exported header and confirm exclusion of unapproved sensitive fields; unauthenticated reports are explicitly labeled internal-use or operational-use if that is the accepted model.

## **15.2 Evidence Lifecycle Rules**

Generated outputs that affect user decisions carry explicit canonical vocabularies. evidence_lifecycle = candidate / tested / skipped / inconclusive / detected-signal / confirmed / rejected / reported. external_response_class = positive / negative / denial / referral / empty / partial / unrelated / timeout / malformed / stale / error / other. output_truth_classification = evidence-backed / simulation / randomizer / mock-data / educational / speculative / entertainment / unsupported. These are independent dimensions and must not be collapsed. A null, failed, negative, skipped, or inconclusive result is valuable evidence - never hide it behind a fake positive or misleading success state.

## **15.3 Truthful Framing and Simulation Boundary**

An explicit user request can authorize fictional, simulated, randomized, educational, speculative, training, demonstration, or entertainment outputs. The request does not make those outputs factual, predictive, validated, safe, or evidence-backed.

Do not reject a requested feature merely because its output is fictional or non-predictive. Classify output_truth_classification exactly as evidence-backed / simulation / randomizer / mock-data / educational / speculative / entertainment / unsupported and require truthful labels, UI copy, report wording, export fields, and operator instructions. The UI may offer a clearly labeled sample, randomizer, simulation, or what-if mode when in scope; it must not smuggle an unsupported claim into button labels, reports, exports, admin actions, warnings, or status badges. Forbidden copy examples: “use these predicted numbers,” “recommended result,” “safe result,” “confirmed finding” — when the system has not proven that claim.

For high-trust domains (finance, health, legal, security, safety, compliance, hiring, fraud, education assessment, scoring, risk classification, prediction), the evidence contract controls whether an output may be framed as advice, recommendation, finding, or prediction. Completion reports state the output classification and whether the decision owner accepted the framing.

## **15.4 Adversarial and Known-Pathology Verification**

Section 7 Adversarial input requirement is the canonical universal rule. When Chapter 15 activates, add the evidence-integrity-specific procedure below for every acceptance-relevant classification, promotion, suppression, filter, skip, validation, parse, scan, import, or report behavior changed or relied upon by the authorization unit:

1\. Define the clean representative input and expected result.

2\. Define the hostile, malformed, noisy, wildcard-like, ambiguous, or known-pathology input that would expose false confidence — the failure that would embarrass the feature if missed.

3\. Define the smallest representative input that proves the invariant (Section 7, Cheap representative verification).

4\. Verify positive behavior, negative-action behavior (Section 7), and truthful reporting for both clean and hostile cases.

5\. Make the fixture/test durable in the approved project state or document the manual regression path before claiming closure. If a real defect exposed an environmental pathology, preserve that pathology as a durable fixture instead of replacing it with a simplified happy-path case.

If only curated happy-path inputs are tested for the acceptance-relevant behaviors governed here, acceptance evidence is insufficient. Apply Section 5 Execution result assessment and Block B2; incomplete evidence does not itself establish partial implementation or demonstrated noncompliance.

## **15.5 Security Scanner False-Positive Disposition**

Security, accessibility, quality, SEO, and static-analysis findings must not be panic-fixed or ignored. Classify each material finding by evidence and exploitability before changing code. A disposition records: finding, tool/source, location, why flagged, whether user input reaches it, source vs generated-artifact location, real exploitability, release-blocker status, disposition (true issue / false positive / accepted risk / deferred / needs review), decision owner, durable-fix need, and follow-up authorization unit or backlog item. If the finding is in generated output, verify whether the source/build path creates it — do not patch generated output alone unless the release requires a temporary mitigation and the durable fix is tracked.
