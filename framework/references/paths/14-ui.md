# **Chapter 14 - UI and Operator Readiness Path**

When to use: new user-facing UI, controls, or surfaces; any UI/UX design or redesign; UI-only change; in-application copy or label correction; mockup-driven work; or operator-readiness/final-mile review.

Companion chapters when applicable: Ch. 20 at release; Ch. 18 for public live surfaces. These rules apply to websites, apps, internal tools, games, shops, automations, dashboards, mobile interfaces, packaged desktop apps, and production-like prototypes.

## **14.1 UI Change Classification Gate**

Classify UI work before coding. Do not solve one class of problem with another class of change.

| **Classification**                      | **Use when**                                                                                                                                                                                                                     | **Do not do**                                                                                                                     |
|-----------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------|
| Copy / label correction                 | In-application text is wrong, confusing, or inconsistent.                                                                                                                                                                        | Do not change workflow or backend.                                                                                                |
| New control or surface                  | User-facing UI that did not previously exist is being added.                                                                                                                                                                     | Do not expand into adjacent redesign or a new interaction model without approval.                                                 |
| Theme / color / contrast                | Dark mode, contrast, color tokens, or readability.                                                                                                                                                                               | Do not rebuild layout or logic.                                                                                                   |
| Component polish                        | A component needs small visual refinement.                                                                                                                                                                                       | Do not change architecture. Do not invent new interactions.                                                                       |
| Layout proportion                       | Widths, spacing, panels, or table dominance are wrong.                                                                                                                                                                           | Do not change workflow, interaction behavior, or component architecture.                                                          |
| Visual direction / substantial redesign | Identity expression, visual system, composition, typography, imagery, motion, responsive expression, or overall design language is being materially redesigned while approved product behavior or workflow may remain unchanged. | Do not silently change product actions, business behavior, workflow semantics, or interaction model unless separately authorized. |
| Workflow / UX correction                | The user path is confusing or blocked.                                                                                                                                                                                           | Do not solve workflow failure with color only. Do not call it polish; preserve working behavior explicitly.                       |
| Layout architecture rebuild             | The app structure is wrong for the intended workflow.                                                                                                                                                                            | Do not implement without requirements and acceptance criteria.                                                                    |
| New interaction model                   | A new way of operating the product is approved.                                                                                                                                                                                  | Do not implement without approved requirements, acceptance criteria, and the applicable representative direction under 14.5.      |

## **14.2 UI Rules**

Mockup fidelity. If a mockup is approved, identify structural zones and match structure before polishing colors or labels.

Layout proportion. Full width does not mean every component stretches edge to edge; size components by task importance.

Existing UI state preservation. Before a UI rebuild, define what behavior must be preserved, moved, removed, or deferred.

Debug control demotion. Developer/debug controls must not become primary operator workflow — automate, hide, move, rename, or remove them before release.

No invented product actions. Do not invent action buttons, menu items, disabled stubs, or workflows not in the current authorization, PRD, or approved backlog. Any visible action must have defined behavior, result/failure handling, and any material endpoint, quota/resource, runtime, or ownership implications. AIPF control machinery is not itself a reason to add product UI.

Stable UI checkpoint, not design freeze. A stable checkpoint blocks unsupported redesign and taste churn; it does not block an explicitly authorized redesign or an evidence-backed improvement tied to an applicable Chapter 14 acceptance criterion. A prior good-enough judgment reduces churn but must not override new evidence or newly authorized design intent (Section 5, Good-enough exit).

Readability floor. Functional text must meet the target platform's accessible legibility floor, considering display density, viewing distance, scaling or zoom, typography, contrast, task importance, and applicable platform/accessibility guidance. Do not rely on microtext for controls, guidance, status, or instructions. Numeric size thresholds are platform- and context-specific and are not AIPF acceptance constants.

Workflow copy truthfulness. UI/report copy must describe what the app actually does - no implied spatial, timing, quota, data, mode, version, package, or workflow behavior that is not true. Copy accuracy is an operator-trust requirement; misleading copy is a workflow-truthfulness defect or accepted limitation, not wording polish.

UI change sequencing. Apply Section 5.3 Authorization-unit coherence. One approved UI outcome may include bounded reference discovery, design direction, visual-system definition, typography, composition/layout, components, imagery/asset treatment, motion, responsive behavior, state treatment, accessibility corrections, rendered verification, and final polish when they share objective, authority, decisions, risk, cost, evidence, rollback/recovery, release, and stop boundaries. Do not split these merely because they are separable disciplines, files, or implementation tasks. Split when a real boundary changes, including an unresolved owner direction choice, new behavior, paid generation, licensing, dependency/architecture, privacy/security, release authority, or another material control change. Any polish must match the selected product identity and approved direction, support the workflow, and preserve protected visual language unless a redesign is approved.

## **14.3 Operator Readiness Rules**

Operator-ready definition. A feature is not operator-ready merely because it is implemented, tested, merged, packaged, or deployed. Operator-ready means a real operator can use it without insider knowledge in the target environment. Use the status vocabulary in Part 3, Block B2 - never collapse states into "done."

Operator-observed defect rule. A screenshot, real-use complaint, log, output file, or observed friction is primary evidence. Classify it as functional defect, UX confusion, readability issue, accessibility issue, visual regression, workflow-truthfulness issue, artifact drift, accepted limitation, or future improvement, and tie it to the affected page, mode, viewport, data state, artifact/version, and operator task before the next prompt. Passing tests and prior acceptance do not rebut operator evidence (Section 5.2, Green-test rebuttal).

Mode-specific review. Classify which modes a UI change affects instead of judging the interface as one state. Common modes: setup/input, upload/import, estimating, running/polling, empty, recovered results, live results, drawer/detail, dashboard/settings, mobile, error, source mode, packaged-artifact mode. Each affected mode states what is preserved, what changes, what must not change, and what evidence proves acceptance.

Screenshot/artifact visual acceptance. Before declaring a UI visually accepted, collect the smallest rendered evidence set that can prove the material visual claims under Section 14.5 Visual Evidence and Acceptance. Use the product support matrix or declared acceptance targets for representative viewports/devices; do not hard-code unrelated sizes. Evidence must show more than absence of overflow: hierarchy, purpose, composition, system coherence, responsive transformation, and any material product-specific or temporal claim must be observable. For packaged desktop apps, include the released artifact when claiming artifact readiness. If a material visual criterion cannot be observed, assign an appropriate capable observer and mark that evidence pending rather than passed.

Public surface and interaction verification. Verify public pages from the perspective of the systems that consume them: browser users, mobile users, keyboard users, assistive technology, and, when SEO/share matters, crawlers and scrapers - full crawler checks in Chapter 18. For custom interactions, source-level accessibility claims are not enough: use an interaction-capable tool or named human observer to verify tab focus, Enter/Space activation, mouse/tap behavior, reduced motion, and focus recovery when those behaviors are acceptance-relevant. Prefer native controls when they satisfy the workflow.

Partial-fix disclosure. Governed by Section 5 (Correction delta discipline): a partial fix states what was fixed, what remains, whether the symptom may recur, and the follow-up.

Quota and resource ownership. Governed by Section 7 (Quota/resource ownership); applies here whenever operator actions or UI verification consume limited resources.

Documentation closure. Governed by Chapter 20 (release closure); operator-readiness review confirms the documentation-closure step was run or explicitly deferred.

## 14.5 Active Design, Design Quality, and Creative Exploration

### Activation and control model

When active: new or substantially redesigned UI/UX; a material new visual world; requests for modern, contemporary, creative, original, bold, immersive, forward-looking, or major visual direction; or repeated rendered evidence that the current design is generic, conventional, visually weak, incoherent, or disconnected from the product. Active design does not make expression mandatory. Use six controls only to the extent they can change acceptance: Design Latitude, Design Direction, Design System, Design Continuity, Design-Quality Floor, and Visual Evidence. Design mandate: actively design rather than merely reproduce familiar conventions, and do not confuse technical correctness with visual acceptance when design quality is in scope.

### Design Latitude

Surface-purpose mode controls design latitude, not product behavior or authority. Use experience / operate / read / mixed. For mixed surfaces, assign the mode per material region. experience applies where presentation, identity, engagement, storytelling, showcasing, differentiation, launch, public communication, or the experience itself is materially part of the surface; it permits the widest visual/compositional latitude when supported by the thesis. operate applies where repeated task completion dominates; preserve task speed, predictability, state clarity, information density, scanning, error prevention, and established workflow conventions unless redesign is authorized. read applies where sustained comprehension dominates; protect readable measure, hierarchy, navigation, information architecture, searchability, and code/data legibility while allowing identity around the reading experience. mixed prevents one design temperament from being forced across materially different regions.

Expression profile. Only when intensity can materially change the design decision, record visual variance / motion intensity / information density = inherit / low / medium / high. These are independent design constraints, not quality scores: high is not better, low is not safer, and routine UI corrections need no profile.

### Design Direction

Product-grounded identity. Distinguish parent-product identity, surface identity, and implementation grammar. Parent identity includes shared trust, accessibility standards, broad typography/color relationships, navigation expectations, and quality characteristics; surface identity includes the purpose, user promise, workflow, emotional tone, domain language, meaningful motifs, and recognizable character of the specific page/feature/mode; implementation grammar includes cards, panels, grids, spacing, borders, component-library conventions, hierarchy, composition, motion, and interaction models. Preserve/evolve identity does not automatically preserve implementation grammar. Existing components and layouts are references, not mandatory templates, unless explicitly protected.

Identity disposition = preserve / evolve / replace / decision needed. Preserve retains protected product/surface qualities without freezing layout grammar. Evolve intentionally extends or replaces composition, spatial behavior, motion, hierarchy, component form, or interaction while retaining protected identity. Replace establishes a new identity direction when the existing one is absent, unsuitable, contradictory, explicitly rejected, or unable to support the approved experience. Decision needed blocks broad design when the protected identity or inheritance boundary is unresolved.

Design thesis. For material new design, major redesign, or a new visual world without an already controlling direction, establish a concise operational thesis before broad implementation. Include only material facts: user/audience, primary job/action/comprehension goal, surface-purpose mode, product/domain/data/workflow context, trust/emotional requirement, source of visual meaning, dominant compositional idea, inherited/evolved identity, signature idea, and expression profile when relevant. A mood label such as modern dark SaaS, premium, futuristic, editorial, minimalist, professional dashboard, or cool animated website is insufficient unless it explains why that direction belongs to this product and user.

Product-specificity test. When differentiated/product-specific design is an acceptance objective, ask whether an unrelated product could use the rendered experience substantially unchanged after replacing only name, logo, and copy. If yes, product specificity is not established unless intentional conventional neutrality is appropriate to the declared surface-purpose mode and explicitly justified. Common controls remain legal; specificity may come from composition, hierarchy, data visualization, typography, imagery, interaction, motion, spatial organization, workflow representation, content structure, meaningful motifs, responsive behavior, product demonstration, or a signature element.

Default-pattern challenge. When active design is triggered because a direction is new, weak, generic, repetitive, or substantially redesigned, identify the obvious category/template default, when material the predictable superficial opposite, and why the selected direction is stronger for this product/user rather than merely different. Do not mechanically choose the familiar template or its anti-template. Common conventions remain valid when they are genuinely the strongest solution.

Expression neutrality and anti-downgrade. AIPF neither prefers nor disfavors large-scale typography, gradients, glow/lighting, heavy or complex motion, 3D/WebGL/spatial media, unconventional composition, strong or extreme asymmetry, unusual scrolling or scroll choreography, immersive interaction, unusual responsive transformation, generative visuals, or other high-expression techniques. When the approved surface purpose, thesis, identity, expression profile, and user experience support them, do not downgrade the direction merely because a conventional implementation is easier, safer-looking, more familiar, more maintainable in the abstract, or more common. Reduce/replace them only when a material governing constraint requires it, including approved intent, task success, accessibility, truthfulness, measured/required performance, platform capability, authority/cost, concrete maintainability consequences that affect acceptance, or another approved requirement. Intensity itself is not failure: heavy animation or extreme asymmetry may be valid; gratuitous animation or excessive asymmetry means the technique failed its purpose/constraints. If the selected direction cannot be implemented inside the authorized constraints, apply Section 5 Intent Preservation and Method failure rules and surface the tradeoff; do not silently substitute a weaker concept.

Reference use. reference_use = controlling-fidelity / system-extraction / inspiration / n-a. controlling-fidelity uses the approved-reference rules below. system-extraction uses a working implementation, design system, style guide, token file, component specimen, or equivalent to extract only relevant reusable type/color/spacing/component/motion/responsive/asset rules; exact available values, when authorized and usable for the project, are stronger evidence than visual guessing, but unrelated branding, behavior, assets, or product semantics are not imported. inspiration extracts named principles such as composition, hierarchy, typography relationship, section pacing, imagery, motion, spatial behavior, state treatment, responsive transformation, data presentation, or interaction without cloning the source. Bounded reference discovery is allowed when the Decision-changing work test says it can change a material direction; stop when evidence is sufficient. External references remain informational until the decision owner makes one controlling.

Representative direction and fidelity. When a material direction genuinely remains unresolved, obtain decision-owner approval on the smallest representative surface/interaction needed to choose it. Approval states whether the result is phase-only or the controlling design direction; when a specific reference controls fidelity, reference_use = controlling-fidelity. Once a controlling direction is approved, exploration closes until reopened; do not create artificial owner gates for later typography, component, motion, spacing, or polish decisions that remain inside the approved direction and Section 5 execution discretion. A controlling reference may be owner-supplied, an existing product surface, screenshot, sketch, wireframe, mood board, design-system example, diagram, human-authored mockup, approved rendered candidate, or sufficiently concrete textual specification. AI-generated references are optional, capability/authority/cost/privacy dependent, and never required. When reference_use = controlling-fidelity, the reference controls the approved composition, hierarchy, relationships, interaction intent, and other named properties; material deviations and causes must be disclosed, and rendered side-by-side comparison is required for fidelity claims.

### Convention lock and design reset

When capable operator/owner evidence rejects a rendered design as generic, repetitive, visually weak, or overly dependent on a specific pattern, lock the rejection narrowly: exact surface, observed grammar, why it failed, prohibited recurrence, scope, objective detection test, and reopen condition. Do not lock broad categories such as cards, hierarchy, spacing, gradients, or asymmetry merely because one implementation failed. A redesign that recolors, re-spaces, or rearranges the same rejected grammar is not materially new. Confirmed recurrence records REJECTED_PATTERN_RECURRED and is assessed only through Block B2.

Rendered distinctness is judged from rendered artifacts, not direction names, prose, CSS differences, or executor confidence. Compare candidate directions on the material dimensions claimed to differ - composition, hierarchy, spatial model, interaction, motion, information model, human-control representation, responsive transformation, or other decision-relevant dimensions. If they look substantially alike on those dimensions before labels are read, distinctness failed.

Escalation: first rejected direction -\> record defect/rejected grammar and issue one bounded correction or replacement; second rejection showing the same grammar -\> stop implementation, activate a design reset, prohibit that grammar, and require materially distinct rendered samples; third rejection or continued recurrence -\> stop open-ended AI exploration and use an owner-approved reference, constrained reference translation, different design-capable executor/tool, human-authored mockup, or explicit accepted limitation. Do not keep generating nominally different versions of the same template.

### Design System

When a unit establishes or materially changes a visual direction, define the smallest visual-system contract needed to keep implementation coherent; no separate file is required. Include only material dimensions: typography roles/hierarchy, color roles, spacing/density, section/content rhythm, container/alignment model, surface separation, border/radius/elevation logic, inherited/new component grammar, icons, imagery/illustration/generative-media language, data visualization, interaction states, responsive transformation, accessibility, motion, and signature treatment. The purpose is to prevent each section/component from independently falling back to familiar defaults.

Signature anchor. Especially for medium/high-expression experience surfaces, consider whether one memorable product-grounded anchor materially strengthens identity, comprehension, demonstration, action, memorability, or emotional fit. It may be a composition, product demo, typography behavior, visualizer/data representation, illustration, physical/domain metaphor, responsive transformation, spatial treatment, motion sequence, 3D scene, or unusual but useful interaction. It is optional, need not animate, and must earn its place. operate/read surfaces may also have signature treatment, but it must not undermine task predictability or reading.

Motion contract. Only when motion materially affects acceptance, define purpose; trigger/input; affected elements; start/end states; sequence; timing/easing/physical relationship when material; interrupt/user-control behavior when material; reduced-motion behavior; and performance constraint when material. Motion may be subtle or extremely elaborate; intensity is not the acceptance criterion. Purpose and rendered execution quality are.

Visual target and asset lock. Before generating, replacing, or fidelity-translating a material visual asset, bind the exact route/surface/mode/slot, deliverable type, explicit non-targets when ambiguous, existing/source asset identity, candidate/reference identity, destination identity, and transport identity available to the executing actor. Executor-local or tool-private paths are not transport identities for another actor unless that actor can access them; use an attachment/file reference, asset ID, immutable URL, hash-bound project file, or confirmed equivalent. Do not allow another route, full-surface mockup, or similarly named asset to silently substitute for the authorized target.

Unrequested visual additions. Classify elements absent from approved requirements as required for accessibility, required for comprehension, optional enhancement, or out of scope. Optional/out-of-scope additions may be proposed but not silently included in an accepted surface. During fidelity work, elements absent from the controlling reference require owner approval unless necessary for accessibility or comprehension; disclose material visual impact.

### Design Continuity

When a thesis or visual system is intended to govern a complete surface, it must remain coherent across the complete material experience. A distinctive opening followed by unrelated generic template sections does not establish full-surface design coherence. Each material region must either advance the selected thesis/system or become intentionally quiet because content/task needs restraint. Quiet is allowed; generic fallback is not the same as intentional quiet. Continuity may survive through typography, color, scale, spacing, compositional logic, surface treatment, interaction, imagery, motion, responsive transformation, and content rhythm. Every section need not add a new gimmick; every section should belong to the same deliberately designed experience.

### Design-Quality Floor

When visual/design quality is materially part of acceptance, functional correctness alone is insufficient. Assess the applicable quality dimensions without a beauty score or preferred aesthetic: purpose fit; hierarchy; system coherence; product specificity when differentiation is intended; composition/proportion/balance/grouping/alignment/pacing/density; craft/finish; interaction and state quality; responsive integrity; motion quality when motion exists; accessibility; and truthfulness. Browser defaults, untouched component-library defaults, inconsistent tokens, arbitrary spacing, unconsidered typography, generic placeholder structures, and unfinished states fail craft unless intentionally part of the approved direction. Responsive acceptance asks whether hierarchy, action, composition, meaning, density, interaction reachability, and the design system survive transformation - not merely whether overflow is absent. A surface may be exceptionally quiet or wildly expressive and pass; the floor asks whether it is considered and well executed.

Correct-but-generic rule. When product-specific visual design is an explicit acceptance objective, technical correctness plus generic visual execution is not sufficient evidence of acceptance. This rule does not turn a routine bug/copy fix into redesign work; it applies only when design quality/product-specific identity is part of the authorized outcome.

### Visual Evidence and Acceptance

Match rendered evidence to the claim being made; do not mandate one universal screenshot list. Static/compositional claims capture enough material regions and representative responsive layouts to assess hierarchy, proportion, composition, visual-system consistency, specificity, and responsive transformation. Operational UI captures only acceptance-relevant states/modes such as empty, populated/dense, running/loading, success/error, selected, detail/drawer, filtering/editing, disabled/permission, responsive, and keyboard/focus. Motion/scroll/immersive claims require the smallest useful set of temporal, scroll, scene, interaction, before-active-after, keyframe, contact-sheet, or short-recording evidence needed to expose intermediate failures; a single hero screenshot is insufficient for a temporal claim. Fidelity uses rendered comparison against the controlling reference on the dimensions it controls. When motion is material, reduced-motion evidence must show a complete, understandable, usable experience rather than merely disabling everything.

Visual evidence capability boundary. Separate source/tool evidence from rendered visual evidence; assign each criterion to an observer with the required capability and confirmed evidence-acquisition feasibility. An executor without suitable rendered-inspection capability must not claim visual balance, hierarchy, spacing quality, absence of overlap, distinctness, fidelity, legibility, motion quality, theme fit, aesthetic success, or design-quality-floor PASS from source inspection alone. Capability-inconsistent PASS evidence is insufficient under Block B2; route the visual criterion to a capable observer/tool or leave the required observation pending.

Acceptance meaning. Section 5 Good-enough exit governs. Canonical acceptance meaning = decision needed / phase-only / accepted limitation / final visual acceptance / deferred improvement. "Good enough for the current phase" maps to phase-only; it is not a second value. Every material visual surface also records exploration status = candidate / approved direction / rejected; fidelity status = not active / active / deviations pending / fidelity confirmed; visual evidence status = unobserved / review pending / reviewed with capable observer and Block B1 attribution; known visual debt; and revisit trigger. Review status records whether observation occurred, not whether it passed; retain the actual result separately. These fields do not replace Block B2.

Rendering model and execution risk. When alignment, responsive geometry, connectors, 3D/spatial composition, layered positioning, or temporal choreography can affect acceptance, declare the rendering model and coordinate/state owner plus the material verification method. Mixed systems are allowed when observable. Section 5 acceptance-threatening risk stop governs unresolved rendering/design strategy risk; feasibility is a constraint, not the default design objective. Do not choose a weaker direction primarily because it is easier or more familiar. UX/accessibility remains a hard floor: expression must not obscure actions, meaning, focus, status, legibility, semantics, responsiveness, truthfulness, safety, or task success.

Creative verification and record. Confirm that the selected design latitude matched the surface; protected identity was preserved/evolved without automatically preserving generic grammar; the thesis is product-grounded; product specificity is established when required; default and anti-default choices were intentional; expression was neither suppressed nor added without purpose; the visual system and thesis continue across the claimed scope; rejected grammar did not recur; accessibility/task clarity remain intact; and material distinctness, fidelity, quality, responsive, and temporal claims are supported by rendered evidence. Use the Section 14.4 UI Authorization Unit Template; do not maintain a parallel design artifact.
