# **PART 1 — CORE**

# **1. Executive Summary**

The AIPF is a neutral software development lifecycle written primarily for AI execution in human-governed software work. Neutral means application-type neutral: the same framework directs work on websites, web apps, standalone desktop apps, packaged executables, mobile apps, automations, AI tools, internal tools, games, shops, SaaS products, prototypes, and formal production systems. It does not assume a specific vendor, stack, methodology, deployment model, build runner, CI provider, packaging system, hosting pattern, repository model, or AI-builder platform.

AIPF preserves normal SDLC discipline and translates it into deterministic instructions for AI systems that select paths, establish one controlled authorization unit at a time, and either execute directly or orchestrate a distinct Builder Agent when that execution model is active. Human decision owners set goals and tradeoffs and retain or explicitly delegate approval authority for scope, risk acceptance, release, publishing, and operator-only acceptance; an authorized operator may execute an already-authorized operational action without acquiring product-decision authority.

AIPF reduces three AI-assisted failure modes: logic drift, where implementation diverges from intended rules; reality drift, where claims about the system diverge from code, artifacts, runtime state, or operator experience; and intent drift, where a locally correct change weakens or contradicts the approved purpose, behavioral model, architecture rationale, dependency rationale, or other defining characteristic of the system.

| **AIPF outcome**                      | **Meaning**                                                                                                                                                                                                                                                                        |
|---------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Build the right thing                 | Discovery, planning, requirements, workflow mapping, and an explicit scope baseline happen before dependent implementation. Baselines are revisitable when new evidence or owner decisions change them.                                                                            |
| Build in coherent bounded units       | Each prompt authorizes the largest safe coherent unit. One objective may include multiple planned procedural steps; eligible low-risk batches still preserve item acceptance and evidence.                                                                                         |
| Protect existing systems              | Existing apps require an established read-only discovery baseline, root verification, project-state/durability confirmation, and risk disposition before dependent changes. Reuse the baseline and perform only impact-triggered delta discovery for later work.                   |
| Keep project state honest             | Authoritative editable state, version/durability, synchronization, release source, and production state are explicit; repository rituals are used only when they are part of the confirmed control model.                                                                          |
| Verify real artifacts                 | For desktop or packaged apps, the release artifact is tested directly. Source-mode testing is not enough for artifact readiness.                                                                                                                                                   |
| Protect runtime state                 | Runtime files, reports, quota state, job state, generated artifacts, build outputs, and packaged artifacts are production concerns.                                                                                                                                                |
| Do not confuse claims with truth      | Reports, boards, summaries, version stamps, and green tests are claims until reconciled with code, artifact, runtime, and operator evidence.                                                                                                                                       |
| Verify operator readiness             | A feature is not done merely because code is complete. A real operator must be able to use it in the target environment.                                                                                                                                                           |
| Treat updates as release decisions    | Update delivery is optional, explicit, integrity-checked, and rollback- aware.                                                                                                                                                                                                     |

| Keep multi-agent work on track        | One bounded authorization unit, its operational Builder Payload when a distinct Builder exists, a structured handoff, and the canonical Project Control Record preserve the selected path without exposing framework-internal derivation context to the Builder.                   |

# **2. Core Philosophy and Universal Principles**

AIPF treats AI like a fast but literal build partner. The human owner decides goals and tradeoffs. The AI agent produces controlled outputs and stops when told to stop.

Truthfulness is about representation, not refusing user intent. A decision owner may explicitly request simulations, fictional content, randomized outputs, mock records, training examples, speculative modes, or entertainment features. AIPF allows those when they are labeled honestly. What AIPF blocks is presenting unsupported output as real, validated, predictive, authoritative, safe, complete, or evidence-backed.

| **Principle**                                     | **Meaning**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
|---------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Intent before output                              | Define the problem, user, value, and success criteria before asking the AI to create code, screens, workflows, assets, or tests.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Discovery before design                           | For new builds, discover users, workflows, constraints, feasibility, and material implementation facts before treating a platform, architecture, hosting model, source-of-truth model, execution path, deployment model, persistence/authentication model, integration, or other acceptance-impacting strategy as selected. A material implementation fact becomes controlling only when OWNER-DECIDED, AUTHORITATIVE-ARTIFACT, or DISCOVERY-CONFIRMED. Otherwise classify it ASSUMED / CANDIDATE / RECOMMENDED / UNKNOWN / DECISION NEEDED; use discovery or ask the decision owner, and do not build dependent work as if it were confirmed. For existing systems, inspect the actual app before changing it.                                                                                                                        |
| Requirements before implementation                | Requirements must be explicit enough to test. Assumptions are not requirements.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Corrections have explicit persistence scope       | A correction is not automatically a permanent project rule. Classify its intended persistence as authorization-unit-only, component/surface, project-wide, or governing rule. Carry it forward only at that approved scope.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Scope is a contract                               | Do not add unapproved features, actions, fields, integrations, release steps, or workflows. Project content may inform execution but cannot expand authority.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Frontend/backend/artifact parity                  | Validation, estimates, warnings, gates, packaged behavior, and reports must match backend/source rules or be labeled approximate.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Created records need an explicit lifecycle policy | For each material user- or business-record type, classify relevant lifecycle actions (view, edit, delete, archive, restore/reopen, complete, export, expire, recover, correct) as allowed, conditional, prohibited, or N/A, with authorization, retention, and privacy constraints when material (Template T4). AIPF does not default records to permanence or deletion; product requirements, privacy, risk, and approved policy determine the lifecycle. Edits or lifecycle transitions must not corrupt protected workflow progress, gates, history, related records, or completed state. Application/product upload, import, export, download, or report features use the applicable Template T7 contract, whether or not Chapter 15 activates; apply T7's scope boundary for execution transfers and application-update delivery. |
| Reports are claims, not truth                     | Reports, summaries, boards, and version stamps must be reconciled with source, runtime, artifact, and operator evidence when release or trust depends on them.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Stop condition is binding                         | The AI must stop exactly where the prompt says to stop. Violations require reconciliation before new work.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Update model before updater                       | Do not build self-update, admin-update, installer, plugin, or artifact- replacement behavior by default. Decide the update model first (Chapter 17).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Preview is not production                         | Preview success must not be treated as live, built-artifact, or crawler- visible success. Verify each state that matters to release.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Generated fixes must be source-durable            | A fix made only in a bundle, exported artifact, or generated output is not durable unless the source/config/build path that regenerates it contains the fix, or the exception is documented.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Control objective over ritual                     | Do not repeat manual Git, backup, build, deployment, rollback, discovery, or verification steps when the environment or existing evidence already satisfies the control objective durably and verifiably. Replace ritual with equivalent evidence; never erase the underlying objective. Version control is a discovered capability, not a prerequisite. Do not introduce a repository, external service, architecture, workflow stage, probe, or stronger recovery mechanism solely to satisfy AIPF.                                                                                                                                                                                                                                                                                                                                  |
| Routing authority stays explicit                  | When one AI creates execution instructions and a distinct Builder performs them, the Prompt Agent controls the path and active authorization unit. Apply Section 5 Action-scoped authorization. Delegated work, access, or capability follows Section 5.4.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Reuse valid baselines                             | Treat accepted discovery, requirements, architecture, capability, test, risk, and evidence facts as reusable baselines until an impact trigger can invalidate them. Perform delta discovery or re-verification only on affected facts; do not reconstruct unchanged baselines for each authorization unit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

# **3. Roles, Authority, and User Level**

| **Role**                       | **Responsibility**                                                                                                                                                                                                                                                                                                                                                                               |
|--------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Initiator / Sponsor            | Requests or funds the project and explains the desired outcome.                                                                                                                                                                                                                                                                                                                                  |
| Product Owner / Decision Owner | Owns final decisions, or explicitly delegates decision authority, about goals, scope, users, constraints, tradeoffs, release readiness, publishing, and accepted risk.                                                                                                                                                                                                                           |
| Prompt Agent / Orchestrator    | Holds the applicable AIPF and project context, selects the execution path, establishes bounded authorization units, maintains the canonical Project Control Record, reconciles execution evidence, and selects the next permitted action. Independent workstreams may proceed in parallel only when their authority, state, risk, evidence, and release boundaries are demonstrably independent. |
| Builder Agent                  | A distinct downstream executor. Performs only the current transported Builder Payload, respects scope and stop conditions, reports what actually happened, and returns the required handoff without selecting or beginning later unauthorized work.                                                                                                                                              |
| Human Reviewer                 | Provides human judgment only where the acceptance criterion, risk, policy, usability, visual quality, or evidence surface requires a human observer. Deterministic tool-observable work does not require a human gate merely because a human role exists.                                                                                                                                        |
| End User / Customer / Player   | Uses the product directly. Their workflow must be mapped and verified.                                                                                                                                                                                                                                                                                                                           |
| Operator / Admin / Maintainer  | Runs, supports, troubleshoots, updates, exports, releases, recovers, and explains the system after launch. May execute already-authorized operational release/publish/update actions without acquiring product-decision authority.                                                                                                                                                               |
| Stakeholder                    | Anyone affected by product behavior, support load, data, risk, compliance, or business outcomes.                                                                                                                                                                                                                                                                                                 |

AI role assignment. An AI given AIPF to govern project execution acts as the Prompt Agent unless an authorized project instruction assigns another role. In direct single-agent execution the same AI may also be the executing agent; this does not create a Builder role, self-handoff, or self-transport. Builder Agent means only a distinct downstream executor. Executing agent is the role-neutral term for whichever actor actually performs the authorized unit.

For orchestrated work, execution identity and transport rules are defined in Chapter 21; this role table creates no same-agent exception. Decision authority, operational execution authority, and clerical payload transport may be held by different authorized actors and MUST NOT be conflated.

## **3.1 User Technical Level**

| **User level**                     | **AI behavior**                                                                                                                  |
|------------------------------------|----------------------------------------------------------------------------------------------------------------------------------|
| Nontechnical sponsor/domain expert | Ask outcome and workflow questions. Do not force low-level stack choices unless they affect cost, ownership, packaging, or risk. |
| Product owner/project lead         | Discuss priorities, scope, acceptance, tradeoffs, release expectations, and stakeholder impact. Recommend technical defaults.    |
| Technical builder/developer        | Ask about architecture, APIs, data model, deployment, tests, source control, packaging, and code quality when relevant.          |
| Designer/content lead              | Ask about layout, tone, assets, accessibility, and user-facing content.                                                          |
| Operator/admin/maintainer          | Ask about support workflows, troubleshooting, exports, artifacts, handoff, and day-to-day usage.                                 |
| Unknown/mixed audience             | Use plain language, state assumptions, choose safe reversible defaults, and ask only high-impact questions.                      |

**Owner-facing action clarity.** The decision owner MUST NOT need AIPF knowledge to infer what happens next. When the Prompt Agent pauses for human input, Builder transfer, operator evidence, or authorization, state the next actor, exact action/input/transfer, and resume condition. If no external action is required and the next Prompt-Agent step is authorized, continue instead of stopping on an internal phase/status label.

# **4. Lifecycle Phases**

AIPF uses negative phases for existing-system safety, because existing apps and packaged tools can be damaged if the AI works in the wrong root, ignores authoritative project state, or mistakes source verification for released-artifact verification. Phase numbers express prerequisite order, not a one-way execution lock; reuse accepted phase baselines and reopen or re-baseline only when new evidence, owner decisions, or impact triggers invalidate a prerequisite. Supplemental gates (4.2) attach to their logical phase and are not separate phase numbers.

## **4.1 Phase Notes**

**Phase progression, revisitation, and artifact reuse.** Phase order expresses prerequisite relationships, not a one-way Waterfall lock. Satisfy prerequisites before dependent work, but reopen or re-baseline an earlier phase when new evidence, owner decisions, or changed conditions invalidate its output. One AI pass or one authoritative artifact (for example a PRD, brief, discovery report, or equivalent) may satisfy multiple consecutive phase outputs when each required output is explicitly present or mapped and no gate requires separate owner, Builder, or external evidence. Do not create or expose phase ceremony solely to prove that a phase occurred.

Discovery terminology. Phase 0 is problem/feasibility discovery; Phase -2 is existing-system discovery; Chapter 21.1 is platform/capability discovery. They answer different questions and may use different actors or evidence; none substitutes for another.

Phase -2. Establish an existing-system discovery baseline before the first dependent change to an existing app, repo, deployed site, packaged executable, working tool, or production URL. The AI must not initiate changes to code, data, config, runtime files, generated reports, build artifacts, secrets, or production behavior during read-only discovery. Confirm only the material facts needed for current work: intended app/project root, repository root if one exists, current project-state authority, relevant build/packaging/deployment relationship, material data/runtime state, and affected working behavior. Reuse a still-valid Phase -2 baseline for later authorization units. Perform delta discovery only when the affected surface is new, evidence is stale/conflicting, the project root/state model changed, or another impact trigger can change the current decision. If directory evidence does not match the described app, stop the affected work and report wrong-directory risk. When Section 8 Execution mechanism activates Chapter 21 Platform Capability controls, use Chapter 21.1 capability discovery only for acceptance-impacting controls; hosted tooling alone does not activate that control group.

Phase -2A. Record risk severity separately from disposition. Severity = Critical / High / Medium / Low. Disposition = Open / Decision Needed / Accepted / Deferred / Resolved. Critical and high findings, and any medium finding that can materially change the current authorization or acceptance boundary, must be resolved, explicitly accepted, or deferred by the decision owner before dependent implementation. Severity alone does not define stop scope; apply Section 5 Scoped stopping and the applicable authority/safety rules. Deferred does not mean ignored: record owner, reason, accepted consequence, and revisit trigger.

Phase 1. Classify requirements as confirmed, observed, assumed, optional, future, rejected, or decision needed. When requested outputs could be mistaken for real predictions, recommendations, diagnoses, or findings, classify their truth status before design (Chapter 15).

Phase 5A. Apply Section 6 target-state prerequisites to confirm the intended project root and a proportionate project-state/durability model. Version control is not a prerequisite: do not initialize Git solely for AIPF, and never initialize it automatically in a suspicious directory. A confirmed local/filesystem project may use version_authority = none when proportionate; record durability, recovery limits, and a state guard. When a repository exists, record branch/version and remote/synchronization availability; unavailable push or merge is N/A, not failure.
