# **Maintaining This Document**

This section governs how AIPF itself is revised. Any human or AI updating this document acts as an editor of the existing AIPF document and must follow these rules before editing. This maintenance context does not create Prompt-Agent/Builder orchestration unless such orchestration is explicitly established. Point every future update prompt at this section first.

M1. One-Home Rule. Every normative rule, definition, and canonical vocabulary/value set has exactly one canonical home. Other prose references it by name. A consuming template MAY project a canonical field or exact enum only when it explicitly identifies the canonical source and does not redefine, narrow, extend, or compete with its meaning; copied normative prose or competing value sets are prohibited.

**M2. Placement decision tree.** Before adding anything, work down this order and stop at the first fit: (1) Amend — if the rule already exists in any form, amend the original in its current home; never add a parallel rule. (2) Universal — if it applies across application paths, put it in Part 1. (3) One path — if it is specific to one existing path, put it in that chapter. (4) Cross-cutting composition — if it belongs to an established cross-cutting control domain (e.g., release evidence, executor integrity), compose it into that existing chapter. A chapter qualifies as a cross-cutting home only when it has a coherent control domain, a clear activation condition, its own rules, playbook, and enforcement template or block, a Path Selector trigger or declared companion relationship, and enough substance to remain useful when composed with more than one work path — composition is not a junk drawer for homeless rules. (5) Shared fields — reusable fields used by multiple paths become a Part 3 block (embedded vocabulary) or template (standalone fillable form). (6) New chapter — only when the topic has a distinct activation condition, coherent control objective, playbook, and enforcement surface that no existing home fits.

M3. Forbidden actions. Do not restate a Part 1 rule inside a chapter - reference it by name. Do not create text in any chapter, playbook, block, or template that narrows, overrides, or conflicts with the rule-precedence statement in How to Use This Document. Do not create a new section when an existing one covers the same activation condition and control objective. Do not create a new template when an existing template plus a field works. Do not add a Path Selector row without writing or extending the corresponding chapter. Split a section only when its activation conditions or control objectives materially differ; title length alone is not a reason to split.

**M4. Update procedure.** AIPF CHANGE = one bounded change objective. For each change: read this section; search for existing coverage; classify the change using M2; normally edit one canonical rule home; write normative procedure for machine interpretation first using deterministic conditions, explicit state, compact mappings, binding stop rules, and minimal ambiguity; run M5; stop. Human readability is secondary and MUST NOT add explanatory prose, duplicated rationale, or ceremony that does not improve AI execution. CONSOLIDATION CHANGE = a bounded change whose objective is to remove cross-document contradiction, duplicated or superseded controls, dead or unreachable controls, dangling references, or canonical-vocabulary drift; it MAY edit multiple homes only as required by that objective and MUST NOT be used to bundle unrelated feature objectives. AIPF VERSION = one released version that MAY contain multiple completed AIPF changes and adds exactly one Appendix A version entry summarizing the release.

M5. Self-check before finishing. PASS only if all are true: each completed AIPF change has one bounded objective; each normative rule/definition/canonical vocabulary has one canonical home; each ordinary change normally edits one home; each consolidation change edits only the homes required by its stated cleanup objective; every chapter remains complete within the portable path package defined in How to Use This Document; every Path Selector row still identifies one primary chapter and required companions/wrappers; Part 1 growth is limited to genuinely universal controls; and no known ambiguity can materially change routing, Compact/Managed treatment, authority, execution identity, transport, project state, evidence interpretation, release behavior, or stop scope. For every changed rule family, inspect all references to it. For every changed canonical vocabulary, enum, or composite status schema, compare every consuming table, template, playbook, example, and handoff against the canonical definition; PASS requires that consumers neither add, rename, omit, merge, nor scalarize values/fields unless the canonical home defines an explicit mapping. For routing changes, verify the stated layer count, deterministic order table, quick-composition rows, and chapter activation homes agree mechanically. For a consolidation change, also inspect the full document for duplicated or superseded controls, dangling references, unreachable/dead controls, competing canonical vocabulary, and artifacts or fields with no consuming rule. Merge or remove only when no distinct authorization, correctness, evidence, recoverability, or risk control is lost. If a change can alter routing, treatment, authority, execution identity, transport, state transitions, evidence classification, release behavior, or stops, impacted static scenario traces MUST pass before release. Run representative fresh-context agent trials for materially distinct affected branches when a suitable independent reader is available; if unavailable, record EMPIRICAL AGENT TRIALS PENDING outside the standard and do not claim measured model compliance from static traces. Retain trial model/settings/document hash when trials are run. Before release, confirm the version contains only completed changes and Appendix A gains exactly one entry for that released version. Low activation frequency, alternate stylistic wording, or theoretical compactness alone is not grounds for further change.

M6. Changelog discipline. Version history lives only in Appendix A, exactly one changelog entry/table row per released AIPF version. A version entry may summarize multiple completed AIPF changes. The front-matter version note describes only the current version.
