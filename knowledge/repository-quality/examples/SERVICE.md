## Strong sample

# Status Echo

Local demonstration service that returns the status of an authorized synthetic task. For maintainers evaluating a service boundary; no production deployment, hosted monitoring, persistent customer data or authentication claim.

### First useful request

When an authorized local fixture server implements GET /status, expected illustrative response for ready state is `{"status":"ready"}`. Use its verified local bind address, not a public endpoint. Document exact setup and request command only after inspecting actual implementation. If service unavailable, distinguish connection failure, non-ready response and actual user failure; don't report uptime from sample JSON.

### Operating boundary

In a real service README, identify supported runtime, configuration keys (names only), trust/auth, environment, readiness vs user outcome, data retention, local first-use, logs and recovery. For AI-backed service also identify model/prompt/skill version, data flow, permissions, host limitations, costs and actual evaluation vs trace. Link approved architecture, privacy and runbook only when present; no placeholder links. Require separate authorization for provisioning or release, no real production credentials.

## Faulty contrast

“Production-ready on every cloud, 100% uptime, free forever, secure by design.” Generic badge and unverified demo link do not establish availability, cost, security or real setup. Do not expose debug listener or upload real data to make the demonstration work.

## Verification plan

Use controlled fixture on permitted loopback; verify ready/nonready and unavailable behaviors, request/state identity and no unintended writes, data boundaries and source-backed claims; observe actual rendering and first-reader interpretation. This document supplies a profile and expected illustration, not runtime/visual evidence.
