# Repository organization, community and operational quality

Examples are illustrative; use actual approved project facts, not invented placeholders or results.

## RQ-D07 — Which repository files and settings are proportionate?

**Applicability / decision and alternatives:** Use essential profile: meaningful README, actual license/rights status, relevant ignore rules, safe setup/source reading, tests and version/status. Public/collaborative add real contributing, support/reporting, SECURITY private route, appropriate conduct, issue/PR forms and history only when useful. Deployable/service add configuration/secret references, runbook, recovery, backup, incident and cost docs. Maintain canonical locations. Verify actual maintainer capacity, owner and community profile/settings; do not promise SLA. Metadata/topics/homepage/social preview require permission and actual rights.

**Counterexample:** A tiny private script gets fake support team, SLA, unused PR templates and license copied from another repo; a public repo exposes sensitive vulnerability reports.

**Observable verification and sources:** Inspect files/templates, actual settings where accessible, reporting route and rights; unknown admin settings explicit. No policy mutation as part of critique. DO-S04–11, DO-S19–25. See [source register](SOURCES.md); no tool execution or rights clearance inferred.

## RQ-D08 — What does repository engineering and security quality require?

**Applicability / decision and alternatives:** Relevant build graph, lockfiles/dependency updates, permissions, action pins and actual tests/CI, reviewed artifact identity, release notes parity, findings and backup/recovery. Compare existing controls first; use itemized Scorecard results, optional Actionlint, other tools only after qualification; no aggregate quality score or blanket compliance. Inspect path filters affecting material docs verification and provider branch protection, disclose unobserved. Separate audit from mutation.

**Counterexample:** Docs-only PR bypasses version tests; good score but an archived mutable action or unsafe release overwrite persists. A policy file is not actual enforcement.

**Observable verification and sources:** Inspect exact CI trigger/task and observed results; verify source/artifact identity and controls with evidence, record future improvement separately unless authorized. DO-S01–03, DO-S12–13, DO-S19–25, DO-S32. See [source register](SOURCES.md); no tool execution or rights clearance inferred.

## RQ-D09 — What can be reused, and how small should the correction be?

**Applicability / decision and alternatives:** Original synthesis and authentic product identity. Record author/source URL/pin or date, exact asset/rights/attribution, allowed use and limitations. Curated list license never clears linked images/fonts/logos or source-available examples; reference-only if unresolved. Preserve existing design and qualifiers for small correction. For new material direction seek owner decision if necessary; apply Chapter 13 source/semantic parity, UI/UX where relevant, QA for actual verification, Security for secrets/rights, Architecture for accuracy and DevOps for operations. No sixth specialist, second authority or required tool.

**Counterexample:** A small typo causes repo-wide visual makeover; a license on template used to claim all embedded logos are free; no owner authority for metadata/publication.

**Observable verification and sources:** Check exact changed/protected content, asset rights, scoped rendered/semantic observation and no unintended settings/release effects. DO-S04–11, DO-S33. See [source register](SOURCES.md); no tool execution or rights clearance inferred.
