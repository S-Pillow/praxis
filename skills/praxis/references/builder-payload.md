# Builder Payload synthesis — Praxis

Prompt Agent guidance for distinct-agent work. AIPF Sections 5–10, Chapter 21 and T1 govern; this reference changes neither their authority nor their required fields. Direct execution uses the applicable operational boundary, not a self-handoff. Load this reference only when preparing or reviewing a Builder Payload.

## Construct the payload

1. Derive the current T1 from the Project Control Record, selected path/treatment and passed Preflight. Keep the Derivation Record Prompt-Agent-side. Resolve material conflicts and missing authority before issuance; only objective, authorized conditional gates may remain under READY WITH CONDITIONS.
2. State one meaningful objective (or eligible batch), the exact target and accepted baseline, required behavior and necessary inputs. Distill approved requirements, protected invariants and selected specialist guidance into operational values. The Builder needs no access to Praxis, AIPF, specialists, catalogs or PRD. For specialist-derived values, carry necessary verified provenance, usage restrictions and approved exact values; reject conflicting candidates. Optional access grants no authority; do not impose a universal prohibition on accessing governing resources. An exercise or unit may explicitly restrict access when its authorized boundary requires it. A stable implementation baseline can replace repeated values only when its controlling identity, accessibility and unchanged relevance are confirmed.
3. Specify actor, actions, surfaces, prerequisites, allowed discretion, forbidden changes and material automatic effects. Use concrete verbs, exact identifiers and values where known. Separate requirements from suggestions and conditional actions. State conditions and failure behavior together. Avoid vague words such as “appropriate”, “modern”, “ensure quality” without acceptance-relevant meaning; never invent a value to achieve apparent precision.
4. Give executable verification and observable acceptance criteria, with named capable observers, evidence/fallback, durability and stop scope. Do not silently reduce product quality, omit adverse states, or substitute weaker evidence for a required observation. Include the matching handoff's material fields in ordinary operational language, using the canonical Block B2 execution outcomes (PASS / PASS WITH NOTES / PARTIAL / FAIL / BLOCKED) rather than inventing alternate status labels.
5. Order instructions by dependency. Satisfy applicable T1 fields without making each a separate heading; combine overlapping actions, targets, constraints, gates, acceptance, closure and stop instructions. State each operational requirement once where practical; repeat only when it materially improves execution reliability. Group shared constraints once; reference only verified accessible implementation inputs. Omit irrelevant history, internal reasoning, unused catalog candidates, duplicate warnings and N/A mechanisms when operationally unambiguous. Use the Compact form only when every canonical eligibility condition passes. For corrections carry the necessary delta and stable baseline, not the original assignment again.

## Review before transport

Quality and correctness precede token efficiency. Use the minimum sufficient instructions for successful execution at the required quality, not the shortest prompt. Check that a competent Builder with only the payload and authorized implementation inputs can act or identify a blocking prerequisite without guessing. Check explicitly for material ambiguity, hidden references, contradictory instructions, missing authority, missing acceptance/evidence, and unresolved prerequisites. For material specialist-derived design, verify the actual retrieval invocation count and applicable contrast pairs/thresholds before issuance; reject instructions whose prescribed values fail required checks. Record source identity with the correct artifact label, distinguish token calculations from rendered observation, and keep derivation evidence Prompt-Agent-side. If any required control is missing, do not issue; resolve or request the decision under AIPF. A score or fluent formatting never substitutes for the canonical issuance gate. Transport only the Builder Payload with SEND TO BUILDER; reconcile the handoff before the next unit.

Use the evaluation rubric in `docs/TESTING.md` for scenario reviews or affected regression, not as a mandatory additional report on every prompt.
